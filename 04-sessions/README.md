# 第 4 章：会话管理与上下文压缩

## 核心概念

到第 3 章为止，我们的 agent 已经能读写文件、执行命令了，但它有两个致命问题：

1. **记不住**：消息列表只存在内存里，进程一退出，所有对话都没了
2. **装不下**：每次调用模型都要把完整历史发过去，一个长任务（读几十个文件、跑几十次测试）很快就会撑爆模型的上下文窗口

本章解决这两个问题，对应 pi 的两块代码：

| 问题 | pi 的方案 | pi 源码 |
|------|-----------|---------|
| 持久化、恢复、分支 | JSONL 会话文件 + id/parentId 树 | `packages/coding-agent/src/core/session-manager.ts` |
| 上下文超限 | 用当前模型把旧历史总结成摘要（compaction） | `packages/coding-agent/src/core/compaction/` |

> 本章引用的 pi 源码均来自提交 `7d75a0e`，行号以该提交为准。

本章的 Python 实现：

本章为便于独立运行，直接使用 OpenAI Chat Completions 消息格式和 bash 工具，重点放在会话与压缩；暂未接入第 2 章的 Provider 抽象和第 3 章的文件工具。`summarize_branch()` 与 `branch_with_summary()` 已实现，交互式导航时自动生成分支摘要、使用真实 usage 判断压缩阈值留作章末练习。

## 第一部分：会话存储

### 为什么选 JSONL？

JSONL（JSON Lines）就是"每行一个 JSON 对象"的文本文件：

```jsonl
{"type":"session","version":1,"id":"9f1c...","timestamp":"2026-10-13T04:00:00+00:00","cwd":"/home/me/proj"}
{"type":"message","message":{"role":"user","content":"帮我看看 main.py"},"id":"a1b2c3d4","parentId":null,"timestamp":"..."}
{"type":"message","message":{"role":"assistant","content":"","tool_calls":[...]},"id":"e5f6a7b8","parentId":"a1b2c3d4","timestamp":"..."}
```

相比"整个会话存成一个大 JSON"，它有三个好处：

- **只追加**：每产生一条消息就往文件末尾写一行，不用重写整个文件，开销是 O(1)
- **崩溃安全**：进程在写某行时崩溃，最多损坏最后一行；读取时跳过坏行即可，前面的历史完好
- **好调试**：`tail -f`、`grep`、`jq` 都能直接用

pi 把会话放在 `~/.pi/agent/sessions/<编码后的工作目录>/<时间戳>_<sessionId>.jsonl`，每个工作目录一个子目录。我们的 Python 版放在 `~/.mini-pi/sessions/`。

### 文件头和 entry

文件第一行是 header，之后每行是一个 **entry**。pi 的定义：

```ts
// packages/coding-agent/src/core/session-manager.ts L41-67
export const CURRENT_SESSION_VERSION = 3;

export interface SessionHeader {
	type: "session";
	version?: number; // v1 sessions don't have this
	id: string;
	timestamp: string;
	cwd: string;
	parentSession?: string;
}

export interface NewSessionOptions {
	id?: string;
	parentSession?: string;
}

export interface SessionEntryBase {
	type: string;
	id: string;
	parentId: string | null;
	timestamp: string;
}

export interface SessionMessageEntry extends SessionEntryBase {
	type: "message";
	message: AgentMessage;
}
```

**TypeScript 语法速查**：

- `export const X = 3;`：导出一个常量，相当于 Python 模块里的 `X = 3`
- `interface SessionHeader { ... }`：描述一个对象"长什么样"，只用于类型检查，运行时不存在。可以理解为 Python 的 `TypedDict`
- `type: "session";`：字段 `type` 的类型是**字面量** `"session"`，即这个字段的值只能是这个字符串
- `version?: number;`：`?` 表示可选字段，可能不存在
- `string | null`：联合类型，"字符串或 null"，相当于 Python 的 `str | None`
- `interface A extends B`：A 继承 B 的所有字段，再加上自己的字段

所以每个 entry 都有 `type / id / parentId / timestamp` 四个公共字段，再根据 `type` 带上各自的数据。entry 的全部类型：

```ts
// packages/coding-agent/src/core/session-manager.ts L183-194
export type SessionEntry =
	| SessionMessageEntry
	| ThinkingLevelChangeEntry
	| ModelChangeEntry
	| UsageEntry
	| CompactionEntry
	| BranchSummaryEntry
	| CustomEntry
	| CustomMessageEntry
	| ContextEditEntry
	| LabelEntry
	| SessionInfoEntry;
```

`A | B | C` 这种写法叫"可辨识联合"（discriminated union）：一个 `SessionEntry` 是其中某一种，靠 `type` 字段区分。常用的几种：

| type | 作用 | 是否进入 LLM 上下文 |
|------|------|------|
| `message` | 一条消息（user / assistant / toolResult） | ✅ |
| `compaction` | 压缩检查点：摘要 + 从哪条开始保留 | ✅（变成一条摘要消息） |
| `branch_summary` | 离开某个分支时对它的总结 | ✅ |
| `custom_message` | 扩展注入到上下文的消息 | ✅ |
| `model_change` / `thinking_level_change` | 切换模型 / 思考等级 | ❌（只记录状态） |
| `label` / `session_info` / `custom` / `usage` | 书签、会话名、扩展私有数据、用量 | ❌ |
| `context_edit` | 对某条已有 entry 的上下文替换/省略 | 影响其目标 entry |

压缩 entry 的结构值得单独看：


`CompactionEntry<T = unknown>` 里的 `<T = unknown>` 是**泛型参数**：`details` 字段的类型由使用者决定，默认是 `unknown`（"任意值，用之前必须先检查"）。关键字段是 `summary`（摘要正文）和 `firstKeptEntryId`（从哪条 entry 开始原样保留）。

### 写入：只追加

```ts
// packages/coding-agent/src/core/session-manager.ts L1172-1195
	_persist(entry: SessionEntry): void {
		if (!this.persist || !this.sessionFile) return;

		if (!this.flushed) {
			if (!this._hasConversation()) return;
			const fd = openSync(this.sessionFile, "wx");
			try {
				for (const e of this.fileEntries) {
					writeFileSync(fd, `${JSON.stringify(e)}\n`);
				}
			} finally {
				closeSync(fd);
			}
			this.flushed = true;
		} else {
			appendFileSync(this.sessionFile, `${JSON.stringify(entry)}\n`);
		}
	}

	private _appendEntry(entry: SessionEntry): void {
		this.fileEntries.push(entry);
		this.byId.set(entry.id, entry);
		this.leafId = entry.id;
		this._persist(entry);
```

两个细节：

1. **延迟落盘**：`flushed` 为 false 时，如果还没有真正的对话（`_hasConversation()`），什么都不写。这样只打开 pi 又马上退出，不会留下一堆空会话文件。第一次真正写入时用 `"wx"` 模式（文件已存在就报错）把内存里攒下的 entry 一次性写进去
2. **之后每条 entry**：`appendFileSync` 追加一行 `JSON.stringify(entry)`

`_appendEntry` 同时更新三样东西：`fileEntries` 数组、`byId` 索引（`Map` 相当于 Python 的 `dict`），以及 **`leafId` 指针**。

### 持久化粒度：turn 不是原子单位

先把三个词的层级对齐：一个 **session** 包含多个 **turn**（从一条 user 消息开始，到模型不再调用工具为止）；一个 turn 内部穿插若干条 assistant 消息和工具结果。**JSONL 的行对应消息，不是 turn**：

| 对象 | 是否对应一行 | 说明 |
|---|---|---|
| turn | ❌ | 文件里没有 turn 容器；边界按“user 消息出现的位置”推导（第二部分选切点用的就是这个） |
| user 消息 | ✅ | 输入即落盘 |
| assistant 消息 | ✅ | 流式输出结束（或被打断）时落盘 |
| 工具调用（toolCall） | ❌ | 嵌在 assistant 那一行的 `content` 数组里，并发调用也不拆行 |
| 工具结果（toolResult） | ✅ 每个一行 | 行内 `toolCallId` 唯一，执行完一个写一行 |

pi 把持久化钩子挂在每条消息的 `message_end` 事件上——**一完成就追加，不等 turn 结束**：

```ts
// packages/coding-agent/src/core/agent-session.ts L1148-1165（节选）
		if (event.type === "message_end") {
			let entryId: string | undefined;
			// ...custom 消息走 appendCustomMessageEntry...
			} else if (
				event.message.role === "system" ||
				event.message.role === "user" ||
				event.message.role === "assistant" ||
				event.message.role === "toolResult"
			) {
				// Regular LLM message - persist as SessionMessageEntry
				entryId = this.sessionManager.appendMessage(event.message);
			}
```

一个“两个并行工具调用 + 总结回复”的 turn，在文件里展开就是 5 行：

```jsonl
{"type":"message","message":{"role":"user","content":"找出所有 TODO"},...}
{"type":"message","message":{"role":"assistant","content":[{"type":"toolCall","id":"c1","name":"grep",...},{"type":"toolCall","id":"c2","name":"read",...}]},...}
{"type":"message","message":{"role":"toolResult","toolCallId":"c1",...},...}
{"type":"message","message":{"role":"toolResult","toolCallId":"c2",...},...}
{"type":"message","message":{"role":"assistant","content":[{"type":"text","text":"共 3 处 TODO…"}]},...}
```

对 pi 的一个真实会话文件（约 370 KB）做一次解剖，观测值逐条印证：

| 统计项 | 观测值 |
|---|---|
| 总行数 | 154 = 1 header + 151 message + 1 `model_change` + 1 `thinking_level_change` |
| message 的 role 分布 | system 1 / user 7 / assistant 73 / toolResult 79 |
| 每条 assistant 内 toolCall 数 | 0 个 9 条；1 个 48 条；2 个 16 条 |
| toolResult 的 `toolCallId` | 79 行互不重复 |
| 平均行大小 | ≈ 2.4 KB |

7 条 user 消息 = 7 个 turn；16 条“一行嵌两个 toolCall”的 assistant 消息说明并发调用不拆行；`model_change` / `thinking_level_change` 是不进上下文的记账行（见上文 entry 类型表）。这个粒度的直接收益是**崩溃损失以一行为界**：turn 处理到任意位置进程死亡，已完成的消息全部完好——这正是“恢复会话”成立的根基，也是下文讨论中断恢复的前提。

### 文件会膨胀吗？

逐行追加意味着文件**只涨不缩**，但先区分两个概念：

- **上下文大小 ≠ 文件大小**。每个请求都要把当前上下文完整重发给模型（无状态 API），token 开销随轮次增长——但那是请求的成本，不是文件的成本。文件里每条消息只存一份：第 50 轮请求重发了前 49 轮的内容，文件不会为此多出任何一行
- **压缩（第二部分）只缩小“发给模型什么”，不缩小文件**。compaction entry 追加一行，被总结的旧消息原样留在文件里——这是刻意设计，`/branch` 回到“被压缩掉”的历史仍然可行

体积本身也不容易失控。一行 ≈ 内容 + 约 100 字节元数据（`id` / `parentId` / `timestamp`），大头是工具输出，而工具输出有硬截断兜底——pi 把 bash 输出截到“最后 2000 行或 50 KB”（先到为准），完整输出另存临时文件：

```ts
// packages/coding-agent/src/core/tools/truncate.ts L11-12
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
```

（mini-pi 第 3 章的对应实现是截尾 4000 字符。）即便模型手滑跑了输出巨大的命令，文件里也只多 50 KB。按上面的实测数据折算，一个重度半天的会话约 1–3 MB，纯文本逐行加载一两秒内完成——膨胀是线性 O(n) 的，量级完全可控。

那为什么不在压缩后**重写文件**、删掉已被总结的旧消息？三个理由：

- 重写是 O(n) IO，而且**写到一半崩溃 = 文件损坏**，丢掉的是整个文件，而不是一行
- append-only 换来：每步写入 O(1)、崩溃时最多坏最后一行、`tail` / `grep` / `jq` 直接可用
- 树形分支要求旧 entry 永远存在——回到三天前的任意一点，需要那三天的历史“还在”

文件真的太大时的逃生通道：pi 的 `/fork` 把当前分支抽成一个**新文件**，只携带从根到目标 entry 的分支路径，`parentId` 链重新连接，header 里记 `parentSession` 指回原文件（`session-manager.ts` L1632 的 `createBranchedSession`）；会话本来就按项目目录分文件存；想清理直接删 `.jsonl` 即可。真到归档敏感的场景，纯文本 JSON 用 gzip 还能再压一个量级——pi 选择明文是为了可调试性。

### 树和分支

每个 entry 的 `parentId` 指向它的上一条。正常对话时是一条直线；但用户可以回到任意历史 entry 重新开始：

```ts
// packages/coding-agent/src/core/session-manager.ts L1573-1584
	/**
	 * Start a new branch from an earlier entry.
	 * Moves the leaf pointer to the specified entry. The next appendXXX() call
	 * will create a child of that entry, forming a new branch. Existing entries
	 * are not modified or deleted.
	 */
	branch(branchFromId: string): void {
		if (!this.byId.has(branchFromId)) {
			throw new Error(`Entry ${branchFromId} not found`);
		}
		this.leafId = branchFromId;
	}
```

`branch()` 只做了一件事：**移动 leaf 指针**。旧的 entry 一个都不删、不改。下一次追加的 entry 以新的 leaf 为父节点，于是文件里形成了一棵树：

```
- [a1] user: 帮我写个排序函数
  - [b2] assistant: 用冒泡排序……
    - [c3] user: 太慢了                ← 旧分支，仍在文件中
  - [d4] assistant: 用快速排序……       ← leaf（新分支）
```

**当前分支** = 从 leaf 沿 `parentId` 一路走到根，再反转：

```ts
// packages/coding-agent/src/core/session-manager.ts L390-416
function buildSessionPath(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionEntry[] {
	const index = buildEntryIndex(entries, byId);
	let leaf: SessionEntry | undefined;
	if (leafId === null) {
		return [];
	}
	if (leafId) {
		leaf = index.get(leafId);
	}
	leaf ??= entries[entries.length - 1];
	if (!leaf) {
		return [];
	}

	const path: SessionEntry[] = [];
	let current: SessionEntry | undefined = leaf;
	while (current) {
		path.push(current);
		current = current.parentId ? index.get(current.parentId) : undefined;
	}
	path.reverse();
	return path;
}
```

语法说明：`leafId?: string | null` 是可选参数；`leaf ??= entries[entries.length - 1]` 的意思是"如果 leaf 是 null/undefined，就赋值为最后一个 entry"（`??=` 是"空值赋值"）；`current.parentId ? a : b` 是三元表达式，等价于 Python 的 `a if current.parentId else b`。

离开一个分支时，可以顺便把它总结一下，带到新分支里（`/tree` 导航时 pi 会询问是否生成摘要）：

```ts
// packages/coding-agent/src/core/session-manager.ts L1595-1625
	/**
	 * Start a new branch with a summary of the abandoned path.
	 * Same as branch(), but also appends a branch_summary entry that captures
	 * context from the abandoned conversation path.
	 */
	branchWithSummary(
		branchFromId: string | null,
		summary: string,
		details?: unknown,
		fromHook?: boolean,
		usage?: Usage,
	): string {
		if (branchFromId !== null && !this.byId.has(branchFromId)) {
			throw new Error(`Entry ${branchFromId} not found`);
		}
		const fromId = this.leafId ?? "root";
		this.leafId = branchFromId;
		const entry: BranchSummaryEntry = {
			type: "branch_summary",
			id: generateId(this.byId),
			parentId: branchFromId,
			timestamp: new Date().toISOString(),
			fromId,
			summary,
			details,
			usage,
			fromHook,
		};
		this._appendEntry(entry);
		return entry.id;
	}
```

### 恢复会话

恢复就是把 JSONL 读回来：逐行 `JSON.parse`，解析失败的行直接跳过，然后把 leaf 设为最后一个 entry。

```ts
// packages/coding-agent/src/core/session-manager.ts L616-624
function parseSessionEntryLine(line: string): FileEntry | null {
	if (!line.trim()) return null;
	try {
		return JSON.parse(line) as FileEntry;
	} catch {
		// Skip malformed lines
		return null;
	}
}
```

`try { ... } catch { return null; }` 等价于 Python 的 `try: ... except Exception: return None`。`as FileEntry` 是类型断言，只告诉编译器"把它当作 FileEntry"，运行时什么都不做。

pi 提供 `SessionManager.create()`（新建）、`SessionManager.open(path)`（打开指定文件）、`SessionManager.continueRecent(cwd)`（恢复该目录下最近的会话，即命令行的 `pi -c`）。

### 中断与崩溃恢复

把粒度和落盘时机串起来，就可以回答一个用户级问题：**turn 处理到一半被打断（Ctrl+C、断电）时，会话处于什么状态？恢复后哪些工作需要重来？**分两种场景。（pi 的 TUI 里中断请求的按键是 Escape；Ctrl+C 默认只清空输入框、双击才退出——无论哪种信号，落到会话层都是同一套 abort 路径。）

**场景一：优雅中断（进程还活着）**

pi 的 abort 是一条“结算”路径，每个环节都留下完整记录：

1. **正在流式生成的 assistant 消息定格落盘**：内容停在当前位置，`stopReason` 记为 `"aborted"`，错误信息一并保存。半截话也是历史，下一次请求模型能看到自己上次说到哪里：

```ts
// packages/ai/src/api/anthropic-messages.ts L920-927（节选）

			for (const block of output.content) {
				delete (block as { index?: number }).index;

			}
			output.stopReason = options?.signal?.aborted ? "aborted" : "error";
```

2. **正在执行的工具收到中止信号，产生合成的错误结果并落盘**。默认的并行批里，尚未轮到的调用也补上同一个结果——保证每个 `toolCall` 都有配对的 `toolResult`：


3. **主循环放弃本轮，什么都不自动重放**：

```ts

```

所以优雅中断后，会话文件是“**协议完整、任务半途**”的状态——结构上没有缺口，turn 做到哪算哪。系统不替你重做任何事：继续、重做还是放弃，由用户的下一个 prompt 决定。pi 在切换、新建、fork 会话前也会先等结算完成，正是为了保证“被打断的 turn（包括工具结果）已经持久化”（`agent-session-runtime.ts` L168 注释：*Settle any active response first so the aborted turn (including tool results) is persisted to the outgoing session before it is replaced.*）。

**场景二：硬崩溃（kill -9 / 断电，没有 abort 机会）**

已落盘的消息都在；正在流式生成的那条 assistant **整个丢失**（那次请求的 tokens 白花）；正在写的那行可能损坏，读取时按上一节的 `parseSessionEntryLine` 跳过。真正的结构风险在这样一个窗口：

```
|← assistant（带 toolCall）已落盘 →|← 崩溃窗口 →|← toolResult 尚未落盘 →|
```

恢复后文件尾部留下**悬空调用**。OpenAI 和 Anthropic 的 API 都要求 tool 结果紧跟发起调用的 assistant 消息（第二部分切点规则也是出于这个原因），直接把悬空调用投影到上下文会被 API 拒绝。而且仅凭文件**无法区分**工具是“根本没执行”还是“执行了、结果没写进来”——自动重放可能重复写文件、重复提交、重发请求。

所以两个实现共同的恢复策略是**补“结构”，不重放“执行”**：

- pi 的优雅路径通过“结算时补结果”从源头避免悬空；硬崩溃留下的残骸同样只能靠补齐结构来修复，而不是靠重放
- mini-pi 第 5 章把这个策略写成了 `repair_pending_results()`：启动时和每轮中断时扫描上下文，为未配对的 toolCall 追加合成错误结果——“本轮中断；执行中的工具可能已有副作用，请先检查实际状态”。只补文件**尾部**的未配对调用，中间出现错乱直接报错，不做猜测性重排

（另一层对比：pi 默认并行批、中止时现补；mini-pi 第 5 章的工具是逐个顺序执行的，不指望“中止时刚好补全”，而是把统一补齐放在 Agent 的启动步骤和每轮的异常路径里——顺带盖住了顺序批中止的悬空问题。）

补充一个值得单独强调的细节：与“补齐对话结构”相对，“重复执行”永远被排除在外——即使悬空的调用其实从未执行，补齐也只会在结果里如实报告中断，由模型和用户决定是否重新发起。恢复的安全性来自“默认不重放”的克制，而不是假设工具幂等。

上述真实会话文件里恰好能同时观察到三类“事故痕迹”：

| 文件中的痕迹 | 含义 |
|---|---|
| 一条 `stopReason: "aborted"` 的空 assistant 消息 | 一次被中止的尝试（内容还没流出一个字），改口重发的消息接在它后面，两次都留在文件里 |
| 三条 `stopReason: "error"` 的空消息（503×2、429×1） | API 失败被完整记录，紧随其后的是自动重试的成功回复 |
| 文件尾部一个没有结果的 toolCall | 解剖文件那一刻**正在执行中**的调用——结果要等工具跑完才落盘 |

空的 aborted / error 消息在 pi 的 Anthropic 适配器投影时会被跳过（`anthropic-messages.ts` L1484 的 `if (blocks.length === 0) continue;`）——留在文件里是历史，出现在请求里是幽灵。turn 的“最后一致状态”就是最后一条成功落盘的消息，**JSONL 的每一行都是一个检查点**。pi 重启后只会提示“上次崩溃”（建议 `/bug` 上报），会话本身要用 `pi -c` / `/resume` 显式恢复。

**本教程的实现边界**：第 4 章的 `main.py` 已按消息逐条落盘——Ctrl+C 打断 `prompt()` 时，已完成的消息不会丢；但还没有悬空调用的补齐逻辑，断在上面的窗口里的话，恢复后投影会触发 API 报错；交互层的 `except (EOFError, KeyboardInterrupt)` 只负责退出循环。补齐作为 Agent 的启动步骤在第 5 章 `agent.py` 实现。

### 从 entry 投影出 LLM 上下文

这是会话管理里最关键的一步：**文件里存的 entry ≠ 发给模型的消息**。pi 分两步把 entry 变成消息。

第一步，`buildContextEntries` 决定"哪些 entry 参与上下文"：

```ts
// packages/coding-agent/src/core/session-manager.ts L476-512
export function buildContextEntries(
	entries: SessionEntry[],
	leafId?: string | null,
	byId?: Map<string, SessionEntry>,
): SessionEntry[] {
	const path = buildSessionPath(entries, leafId, byId);
	let compaction: CompactionEntry | null = null;

	for (const entry of path) {
		if (entry.type === "compaction") {
			compaction = entry;
		}
	}

	if (!compaction) {
		return path;
	}

	const compactionIdx = path.findIndex((entry) => entry.id === compaction.id);
	if (compactionIdx < 0) {
		return path;
	}

	const contextEntries: SessionEntry[] = [compaction];
	let foundFirstKept = false;
	for (let i = 0; i < compactionIdx; i++) {
		const entry = path[i];
		if (entry.id === compaction.firstKeptEntryId) {
			foundFirstKept = true;
		}
		if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
			contextEntries.push(entry);
		}
	}
	contextEntries.push(...path.slice(compactionIdx + 1));
	return contextEntries;
}
```

规则：

- 当前分支上没有压缩 → 整条分支都参与
- 有压缩 → 取**最新的** compaction entry 放在最前面，然后是 `firstKeptEntryId` 起、到 compaction 之前的 entry（被保留的近期消息），再加上 compaction 之后新产生的 entry
- 更早的 entry 仍在文件里，但不再发给模型

第二步，`sessionEntryToContextMessages` 把每个 entry 变成 0~N 条消息：

### Python 实现：session.py

我们的 `SessionManager` 用 OpenAI 的消息格式直接存储（`role` 为 `user` / `assistant` / `tool`）：

```python
class SessionManager:
    def _append(self, entry: dict) -> str:
        entry.setdefault("id", _new_id(self.by_id))
        entry.setdefault("parentId", self.leaf_id)      # 父节点 = 当前 leaf
        entry.setdefault("timestamp", _now())
        self.entries.append(entry)
        self.by_id[entry["id"]] = entry
        self.leaf_id = entry["id"]                      # leaf 前进
        if self.path:
            with open(self.path, "a", encoding="utf-8") as f:
                f.write(json.dumps(entry, ensure_ascii=False) + "\n")
        return entry["id"]

    def branch(self, from_id: str) -> None:
        if from_id not in self.by_id:
            raise KeyError(f"Entry {from_id} not found")
        self.leaf_id = from_id                          # 只移动指针

    def get_branch(self, leaf_id=None) -> list[dict]:
        cur = self.by_id.get(leaf_id or self.leaf_id) if (leaf_id or self.leaf_id) else None
        path = []
        while cur:
            path.append(cur)
            cur = self.by_id.get(cur["parentId"]) if cur.get("parentId") else None
        return list(reversed(path))
```

`build_context_entries()` 与 pi 的 `buildContextEntries` 规则一致，`build_context()` 再用 `entry_to_messages()` 把 entry 投影成 OpenAI 消息。为了简化，我们没有实现 pi 的延迟落盘（新会话会立即写 header），也没有实现 `context_edit`、`label` 等类型。

### 什么时候压缩？三种触发方式

pi 里压缩有三个入口，对应事件里的 `reason: "manual" | "threshold" | "overflow"`：

**1. 阈值（threshold）**：估算的上下文 token 超过"窗口 - 预留"时触发


```ts

 * Check if compaction should trigger based on context usage.
 */
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;

```

默认值：`reserveTokens = 16384`，`keepRecentTokens = 20000`（`settings-defaults.ts` 中的 `SETTINGS_DEFAULTS.compaction` 也是同样的值，用户可在 settings 中按模型覆盖）。以 128K 窗口的模型为例，上下文超过 `128000 - 16384 = 111616` tokens 就会压缩。预留的 16384 tokens 留给模型的回复和摘要本身。

pi 在每次请求模型前、以及每轮 agent 结束后都会做这个检查。上下文 token 优先用上一次 API 返回的真实 `usage`，在它之后新增的消息再用估算补上（`estimateContextTokens`）。

**2. 溢出（overflow）**：API 直接报错"上下文超长"。pi 的处理是：把这条失败的 assistant 消息从上下文里省略，压缩，然后**自动重试一次**；如果重试后仍然溢出，就放弃并报错：

**3. 手动（manual）**：用户输入 `/compact`，后面可以跟自定义说明：

### 摘要用哪个模型？

**就用当前会话正在使用的模型**。`compact()` 接收的 `model` 参数就是会话当前的模型，没有单独配置"压缩模型"。好处是不用额外配置 API key；代价是压缩本身也消耗当前模型的 token。摘要请求的输出上限是 `0.8 × reserveTokens`（默认约 13107 tokens），并显式关闭提示缓存（`cacheRetention: "none"`）。

### 估算 token：chars / 4

```ts
// packages/coding-agent/src/core/compaction/compaction.ts L294-349
/**
 * Estimate token count for a message using chars/4 heuristic.
 * This is conservative (overestimates tokens).
 */
export function estimateTokens(message: AgentMessage): number {
	let chars = 0;

	switch (message.role) {
		case "system": {
			const system = message as SystemMessage;
			chars = estimateTextAndImageContentChars(system.content);
			if (system.sections) {
				for (const section of Object.values(system.sections)) {
					if (section) chars += section.length;
				}
			}
			if (system.toolsAdded) chars += JSON.stringify(system.toolsAdded).length;
			return Math.ceil(chars / 4);
		}
		case "user": {
			chars = estimateTextAndImageContentChars(
				(message as { content: string | Array<{ type: string; text?: string }> }).content,
			);
			return Math.ceil(chars / 4);
		}
		case "assistant": {
			const assistant = message as AssistantMessage;
			for (const block of assistant.content) {
				if (block.type === "text") {
					chars += block.text.length;
				} else if (block.type === "thinking") {
					chars += block.thinking.length;
				} else if (block.type === "toolCall") {
					chars += block.name.length + JSON.stringify(block.arguments).length;
				}
			}
			return Math.ceil(chars / 4);
		}
		case "custom":
		case "toolResult": {
			chars = estimateTextAndImageContentChars(message.content);
			return Math.ceil(chars / 4);
		}
		case "bashExecution": {
			chars = message.command.length + message.output.length;
			return Math.ceil(chars / 4);
		}
		case "branchSummary":
		case "compactionSummary": {
			chars = message.summary.length;
			return Math.ceil(chars / 4);
		}
	}

	return 0;
}
```

`switch (message.role) { case "user": ... }` 相当于 Python 的 `match message.role: case "user": ...`；`Math.ceil` 是向上取整。注释说这个估算是"保守的（偏高）"——对英文和代码基本成立，因为英文平均一个 token 约 4 个字符。

**但对中文不成立。** 一个汉字在常见分词器中通常约占 1 个 token（具体取决于分词器），而 chars/4 只把它算作 0.25 个 token，**低估约 4 倍**。一段 4 万字的中文对话，pi 估算约 1 万 tokens，实际可能接近 4 万。好在 pi 的阈值判断优先使用 API 返回的真实 `usage`，估算只用来补"最后一次 usage 之后新增的消息"和计算切点；但切点估算偏低意味着"保留最近 20000 tokens"实际会保留更多。

我们的 Python 版做了一个 CJK 感知的估算器：

```python
def estimate_text_tokens(text: str) -> int:
    cjk = sum(1 for ch in text if is_cjk(ch))   # 汉字、假名、韩文、全角标点
    other = len(text) - cjk
    return cjk + math.ceil(other / 4)            # CJK 每字 1 token，其余 chars/4
```

```python
>>> naive_estimate("这是一个用于测试的中文句子")       # pi 的做法
4
>>> estimate_text_tokens("这是一个用于测试的中文句子")  # CJK 感知

```

### 切点选择：保留多少、从哪里切

压缩不是把所有历史都变成摘要，而是**保留最近约 `keepRecentTokens`（默认 20000）tokens 的原始消息**，只总结更早的部分。从最新消息往回累加 token，超过预算的那个位置就是切点：


```ts
// packages/coding-agent/src/core/compaction/compaction.ts L430-501
/**
 * Find the cut point in session entries that keeps approximately `keepRecentTokens`.
 *
 * Algorithm: Walk backwards from newest, accumulating estimated message sizes.
 * Stop when we've accumulated >= keepRecentTokens. Cut at that point.
 *
 * Can cut at user OR assistant messages (never tool results). When cutting at an
 * assistant message with tool calls, its tool results come after and will be kept.
 *
 * Returns CutPointResult with:
 * - firstKeptEntryIndex: the entry index to start keeping from
 * - turnStartIndex: if cutting mid-turn, the user message that started that turn
 * - isSplitTurn: whether we're cutting in the middle of a turn
 *
 * Only considers entries between `startIndex` and `endIndex` (exclusive).
 */
export function findCutPoint(
	entries: SessionEntry[],
	startIndex: number,
	endIndex: number,
	keepRecentTokens: number,
): CutPointResult {
	const cutPoints = findValidCutPoints(entries, startIndex, endIndex);

	if (cutPoints.length === 0) {
		return { firstKeptEntryIndex: startIndex, turnStartIndex: -1, isSplitTurn: false };
	}

	// Walk backwards from newest, accumulating estimated message sizes
	let accumulatedTokens = 0;
	let cutIndex = cutPoints[0]; // Default: keep from first message (not header)

	for (let i = endIndex - 1; i >= startIndex; i--) {
		const entry = entries[i];
		const messageTokens = sessionEntryToContextMessages(entry).reduce(
			(sum, message) => sum + estimateTokens(message),
			0,
		);
		if (messageTokens === 0) continue;
		accumulatedTokens += messageTokens;

		// Check if we've exceeded the budget
		if (accumulatedTokens >= keepRecentTokens) {
			// Prefer the closest valid cut point at or after this entry. If trailing
			// tool results exceed the budget by themselves, keep their preceding
			// assistant tool call instead of falling back to the first message.
			cutIndex = cutPoints.find((candidate) => candidate >= i) ?? cutPoints[cutPoints.length - 1];
			break;
		}
	}

	// Scan backwards from cutIndex to include adjacent metadata entries that do not affect context.
	while (cutIndex > startIndex) {
		const prevEntry = entries[cutIndex - 1];
		// Stop at compaction boundaries or context-visible entries.
		if (prevEntry.type === "compaction" || sessionEntryToContextMessages(prevEntry).length > 0) {
			break;
		}
		cutIndex--;
	}

	// Determine if this is a split turn
	const cutEntry = entries[cutIndex];
	const startsTurn = isTurnStartEntry(cutEntry);
	const turnStartIndex = startsTurn ? -1 : findTurnStartIndex(entries, cutIndex, startIndex);

	return {
		firstKeptEntryIndex: cutIndex,
		turnStartIndex,
		isSplitTurn: !startsTurn && turnStartIndex !== -1,
	};
}
```

关键规则：**切点永远不能落在 tool 结果上**。

原因：OpenAI 和 Anthropic 的 API 都要求 tool 结果紧跟在发起调用的 assistant 消息之后。如果保留区以一条孤立的 tool 结果开头（它的 tool_call 已经被总结掉了），API 会直接报错。所以合法切点只有 user、assistant 等消息；切在一条带 tool_call 的 assistant 消息上时，它后面的 tool 结果自然会被一起保留。

`cutPoints.find((candidate) => candidate >= i) ?? cutPoints[cutPoints.length - 1]` 的含义：`(candidate) => candidate >= i` 是箭头函数（相当于 `lambda candidate: candidate >= i`），`find` 返回第一个满足条件的元素，找不到返回 `undefined`；`??` 表示"左边是 null/undefined 时取右边"。也就是：取第 i 条或之后最近的合法切点；如果尾部的 tool 结果本身就超了预算，退回到最后一个合法切点（也就是那条发起调用的 assistant 消息）。

> 实际运行时 pi 调用的是基于投影 entry 的 `findProjectedCutPoint`（同文件 L802-870），规则相同，另外处理了溢出恢复时被省略的失败回复。

### 拆分的轮次：turn prefix

"一轮"（turn）从一条 user 消息开始，包含之后所有的 assistant 回复和 tool 调用。如果一轮特别长（比如一个任务连续调用了 50 次工具），切点可能落在这一轮中间——这叫 **split turn**。

此时这一轮的前半段（从 user 消息到切点）既不在保留区里，又不适合和更早的历史混在一起总结（它是"正在进行的工作"）。pi 的做法是**分两次总结**：

- 更早的历史 → 用常规摘要提示词
- 这一轮的前半段 → 用专门的 turn prefix 提示词，输出上限是 `0.5 × reserveTokens`

然后合并：

- **固定的 Markdown 结构**（Goal / Constraints / Progress / Key Decisions / Next Steps / Critical Context）：让摘要可预测，也方便下一次增量更新时逐节合并

### 压缩之后：产物落盘，投影复用

提示词决定了请求端的样子；真正值得一问的是**这笔请求换回来的是什么**。沿着一笔具体的数据流走一遍。

假设会话里已积累 120K tokens 的原始消息（编号 e1~e11），估算 120K > 阈值 111K，压缩触发，`find_cut_point` 选出切点 `e9`。摘要模型收到一次普通请求（输入就是上面描述的 `<conversation>` 序列化文本），返回的东西——即**压缩产物**——是一份几 KB 的固定格式 markdown 文档：

```markdown
## Goal
- 修复 test_main.py 中的两个测试失败

## Constraints & Preferences
- 不修改公共 API

## Progress
### Done
- [x] 通读 test_main.py 和 main.py
- [x] 定位第一个失败：add() 未处理负数

### In Progress
- [ ] 修复第二个失败

## Key Decisions
- **修复放在 _normalize()**: 保持公共 API 不变

## Next Steps
1. 补 _normalize() 的边界分支
2. 重跑 pytest

## Critical Context
- 报错信息: AssertionError: add(-1, 1) == 0 failed
- 相关实现在 src/main.py L40-64
```

产物不是什么数据结构，也没有别的附件——**就是这么一段字符串，加上代码算好的切点坐标**。它立刻落盘，追加成一行：

```jsonl
{"type":"compaction","id":"cf9a1b2c","parentId":"e11","timestamp":"...",
 "summary":"## Goal\n- 修复 test_main.py……（上文全文）",
 "firstKeptEntryId":"e9","tokensBefore":120428}
```

两个字段各司其职：`summary` 是模型的“浓缩记忆”，`firstKeptEntryId` 声明“从哪段原文起继续原样保留”。**e1~e8 的原始消息一行都没删**（对照第一部分“文件会膨胀吗”：压缩缩小的是发给模型的内容，不是账本本身）。`compact()` 返回的字典还附带 `tokensAfter`——投影重算一次上下文得到的“压缩后尺寸”，仅用于日志展示。

“复用”说的正是接下来这件事。下一次——以及之后的每一次——请求模型，投影出的消息数组长这样：

```
[
  system    系统提示词
  user      "The conversation history before this point was compacted…
            <summary>…compaction entry 的 summary 字段原文…</summary>"
  assistant e9 的消息原文      ┐
  tool      e10 的结果原文      ├ 保留区（e9 起）
  assistant e11 的消息原文     ┘
  user      新输入
]
```

这个数组就是“上下文投影”：每次请求前现拼，拼完即弃。但**数组里每个元素的正文在盘上都有归属**——摘要来自 compaction entry 的 `summary` 字段，其余消息来自原始 entry。所以投影从来不需要存盘：它是账本的“读取结果”，不是需要记下的“新事实”。

把三个容易混淆的角色排个座次，纪律就立住了：

| 角色 | 何时发生 | 成本 |
|---|---|---|
| 压缩动作（一次摘要 LLM 调用） | 只在上下文再次过阈值的瞬间 | 一次 API 调用 |
| 压缩产物（compaction entry） | 跟着压缩动作写一次 | 一行 append，此后终身复用 |
| 上下文投影（消息数组） | 每次请求前 | 拼 JSON 的微秒级开销，零 API 调用 |

压缩是**稀有事件**。以 128K 窗口、默认保留 20K 计，压缩刚结束时上下文只剩“摘要 + 保留区”约 30K，要再攒 8 万多新 token 才会碰到第二次阈值；两次压缩之间的所有请求——几十轮对话、成百上千次工具调用——复用的都是同一行 compaction entry。第二次触发时改用增量更新提示词（旧摘要 + 新消息 → 合并出新摘要），旧 entry 仍在文件里，但投影只认路径上**最新**的那条。

一句话：**菜谱记账一次，每次做菜按菜谱现炒，炒好的菜上桌即弃。**

这个机制还有两个附带保护：

- 如果分支的最后一个 entry 已经是 compaction，`prepare_compaction` 直接返回（避免连续压缩）
- 摘要请求如果因为输出上限被截断（`finish_reason == "length"`），抛错而不是保存一份残缺的摘要

## Python 实现：compaction.py

### 阈值

```python
@dataclass
class CompactionSettings:
    enabled: bool = True
    reserve_tokens: int = 16384      # pi 默认值
    keep_recent_tokens: int = 20000  # pi 默认值


def should_compact(context_tokens, context_window, settings) -> bool:
    if not settings.enabled:
        return False
    return context_tokens > context_window - settings.reserve_tokens
```

### 切点：永不拆开 tool_call / tool 结果

```python
def is_cut_point(e: dict) -> bool:
    """可以作为"保留区第一条"的 entry：不能是 tool 结果"""
    return any(m.get("role") != "tool" for m in _entry_messages(e))


def find_cut_point(entries, start, end, keep_recent_tokens) -> CutPoint:
    cut_points = [i for i in range(start, end) if is_cut_point(entries[i])]
    if not cut_points:
        return CutPoint(start, -1, False)
    acc = 0
    cut = cut_points[0]
    for i in range(end - 1, start - 1, -1):          # 从最新往回走
        t = sum(estimate_message_tokens(m) for m in _entry_messages(entries[i]))
        if t == 0:
            continue
        acc += t
        if acc >= keep_recent_tokens:
            cut = next((c for c in cut_points if c >= i), cut_points[-1])
            break
    if is_turn_start(entries[cut]):
        return CutPoint(cut, -1, False)
    ts = next((i for i in range(cut, start - 1, -1) if is_turn_start(entries[i])), -1)
    return CutPoint(cut, ts, ts != -1)               # 切在轮次中间 → split turn
```

### 摘要生成（OpenAI SDK）

```python
def _complete(client, model, prompt_text, max_tokens) -> str:
    resp = client.chat.completions.create(
        model=model,
        messages=[{"role": "system", "content": SUMMARIZATION_SYSTEM_PROMPT},
                  {"role": "user", "content": prompt_text}],
        max_tokens=max_tokens,
    )
    choice = resp.choices[0]
    if getattr(choice, "finish_reason", None) == "length":
        raise RuntimeError("Summarization failed: generation hit the token cap and the summary is incomplete")
    return choice.message.content or ""


def generate_summary(client, model, messages, reserve_tokens,
                     custom_instructions=None, previous_summary=None) -> str:
    max_tokens = math.floor(0.8 * reserve_tokens)
    base = UPDATE_SUMMARIZATION_PROMPT if previous_summary else SUMMARIZATION_PROMPT
    if custom_instructions:
        base = f"{base}\n\nAdditional focus: {custom_instructions}"
    prompt = f"<conversation>\n{serialize_conversation(messages)}\n</conversation>\n\n"
    if previous_summary:
        prompt += f"<previous-summary>\n{previous_summary}\n</previous-summary>\n\n"
    prompt += base
    return _complete(client, model, prompt, max_tokens)
```

`compact()` 把 `prepare_compaction()`（找切点、收集要总结的消息、继承上次的摘要和文件列表）、摘要生成（含 split turn 的两段式总结）和 `session.append_compaction()` 串起来。`prompts.py` 中的提示词是从 pi 源码逐字复制的。

摘要使用与对话相同的 OpenAI 客户端和模型（`OPENAI_MODEL`，默认 `gpt-4o-mini`）。如果想用 Claude，可以参照第 2 章的适配器替换 `_complete`，本章不展开。

### 三种触发方式（main.py）

```python
class Agent:
    def maybe_compact(self) -> bool:
        """阈值触发：每次调用模型前检查"""
        tokens = estimate_messages_tokens(self.context_messages())
        if should_compact(tokens, self.context_window, self.settings):
            return self.compact() is not None
        return False

    def _call_llm(self):
        """溢出触发：API 报上下文超限 → 压缩 → 重试一次"""
        try:
            return self.client.chat.completions.create(
                model=self.model, messages=self.context_messages(), tools=TOOLS)
        except Exception as e:
            if not is_context_overflow(e):
                raise
            if self.compact() is None:
                raise
            return self.client.chat.completions.create(
                model=self.model, messages=self.context_messages(), tools=TOOLS)
```

手动触发：在交互界面输入 `/compact` 或 `/compact <说明>`。

`is_context_overflow()` 通过错误码 `context_length_exceeded` 和常见报错文本识别溢出。pi 的对应实现（`packages/ai/src/utils/overflow.ts` 的 `isContextOverflow`）覆盖了更多厂商的报错格式，还会检查"成功返回但 usage 已超过窗口"的情况。

我们的阈值判断只用估算值；pi 优先使用 API 返回的真实 usage。读者可以把 `response.usage.total_tokens` 记录到 assistant entry 里来改进（见练习 2）。

## 练习

### 练习 1：/tree 导航时生成分支摘要

**目标**：实现 `/goto <id>` 命令——在切换分支前，用 `summarize_branch()` 总结当前分支中"即将离开"的部分（从共同祖先到当前 leaf），再调用 `branch_with_summary()`。

**提示**：先分别求出旧 leaf 和目标 entry 到根的路径，找到最近的共同祖先，只总结共同祖先之后的那段。

### 练习 2：用真实 usage 判断阈值

**目标**：把 OpenAI 响应里的 `response.usage` 存进 assistant entry（例如 `entry["message"]["usage"]`），阈值判断时优先使用"最后一条带 usage 的 assistant 消息的 `total_tokens` + 之后新增消息的估算值"，与 pi 的 `estimateContextTokens` 一致。

**注意**：压缩之后，保留区里旧消息的 usage 反映的是压缩前的大上下文，不能再用（pi 用时间戳和压缩 entry 比较来排除）。
