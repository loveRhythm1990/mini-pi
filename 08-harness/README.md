# 第 8 章：Harness——设计思路、取舍与验证

## 本章要回答什么？

前七章实现了一个能读取文件、执行命令、修改代码、保存会话的 Agent。本章讨论这些能力如何分工，以及如何判断一种设计是否值得采用。

贯穿本章的问题是：**增加这个机制，究竟减少了哪一种失败？我们怎么知道？**

本章不增加运行入口。下面的例子是概念示例；设计分析是本教程的判断，引用的作者观点和实验结果会单独标明。

## 第一部分：为什么简单循环能工作？

最小 Agent 循环可以写成：

```text
组织上下文 → 调用模型 → 执行工具 → 收集结果 → 更新上下文
                 ↑                              │
                 └──────────────────────────────┘
```

循环本身很短，但它连接的组件并不简单：

| 组件 | 承担的工作 |
|---|---|
| LLM | 分析任务、解释代码、提出假设、选择下一步操作 |
| 开发环境 | 提供文件、编译器、测试、Git、进程和网络等能力 |
| Harness | 组织模型请求、执行调用、维护状态，并处理控制路径 |
| 开发者与验收流程 | 提供需求、项目约束，检查结果是否满足目标 |

因此，代码量少并不意味着整个系统的能力少。一个几十行的循环可以调用复杂模型，也可以通过 shell 使用成熟的开发工具。

但工具的能力覆盖与任务成功率是两件事：bash 可以执行测试，不保证模型会选择正确的测试；模型可以读取整个文件，不保证它会发现重要约束。

## 第二部分：Prompt、上下文与 Harness

**Prompt** 通常指任务和行为指令；**上下文**是一次模型调用实际收到的全部信息，包括指令、对话、代码、工具定义和工具结果。不同接口的具体表示不同，工具结果通常是协议消息或内容块。

**Harness** 是围绕模型工作的运行系统。它可以包含上下文构建、工具分发、状态保存、权限检查、预算、中断、重试和展示等部分。并非每个 Harness 都实现这些能力。

从模型的视角看，工具结果也是上下文。但从系统的视角看，工具执行还产生外部效果：

```text
模型输出：把 config.py 中的超时时间改为 30
工具执行：实际修改磁盘上的 config.py
反馈消息：修改成功
```

只添加“修改成功”消息不会改变文件；修改文件却没有准确反馈，也会让模型根据错误状态继续行动。

所以 Harness 要同时保证两条路径：

- 信息路径：模型看到什么，结果如何表示，历史如何保留。
- 行动路径：调用是否实际执行，失败或中断后环境处于什么状态。

第 3 章的工具错误和第 7 章的中断处理，都说明这些工作需要真实的程序逻辑。提示词可以要求模型谨慎，但不能代替进程清理或访问控制。

## 第三部分：Agent 怎样理解代码？

以本教程实现为例，模型通过搜索和文件读取取得代码，再根据返回内容决定下一步。它通常不会在开始时完整理解整个仓库，而是逐步探索：

```text
搜索符号 → 读取实现 → 查看调用方与测试 → 形成假设
                                             ↓
补充阅读 ← 分析失败结果 ← 编译与测试 ← 修改代码
```

这里的 grep / rg 负责定位文本，read 负责取得代码内容，理解和选择由模型完成。运行测试、查看异常堆栈或调试程序，可以增加对实际行为的观察。

### 检索的形态阶梯：grep、repo map、语言服务器

文本搜索不是唯一的检索方案，它是一条成本阶梯的最低一级。pi 的内置工具可以当作这条阶梯的实证注脚：提交 `8bb180b` 下 [`packages/coding-agent/src/core/tools/`](https://github.com/earendil-works/pi/tree/8bb180bec133199c913ca8ef9bb30bd9ab12a72b/packages/coding-agent/src/core/tools) 里用户可调用的内置工具是 `bash`、`read`、`write`、`edit`、`grep`、`find`、`ls`，全部文本级、无状态、零索引；language server 在文档中只出现在权限说明里（[security.md](https://github.com/earendil-works/pi/blob/8bb180bec133199c913ca8ef9bb30bd9ab12a72b/packages/coding-agent/docs/security.md) L3：“扩展、包安装器、语言服务器及其他子进程与宿主同权限运行”）——即内核不内置，需要的人经扩展自己接。

为什么最低一级就够用？两条理由。第一，探索循环的每次往返都经过一次模型级的语义过滤：grep 返回十个命中，模型读上下文就能判断哪三个是真的，查询不需要一次就准。第二，验证兜底比查询兜底更强：找漏了引用，测试、编译和类型检查会在执行时暴露——这些可执行反馈比语言服务器的“查找引用”更严格。Harness 的基本取向由此形成：**用可执行反馈验证理解，而不是用查询保证理解**。

盲区同样真实：同名的变量、注释和字符串会带来假命中与漏报；动态语言的方法分发靠文本追不到；大规模重命名时漏掉一个调用点而测试没有覆盖，就是隐患。当这类问题从“可能发生”变成“反复出现”，才值得考虑阶梯的更高一级：

| 形态 | 代表做法 | 成本 | 提供什么 |
|---|---|---|---|
| 文本检索 | grep / rg + read | 零状态、零维护 | 定位；判别交给模型 |
| 临时符号脚本 | bash 里跑 ctags / tree-sitter 生成符号表 | 一次性产生，无状态 | 文本难以直接给出的符号清单 |
| repo map | [Aider](https://aider.chat/docs/repomap.html)：tree-sitter 抽符号 + PageRank 排序，塞进系统提示，随编辑增量 | 每会话维护一份摘要 | 仓库结构与关键符号的常驻鸟瞰 |
| IDE 上下文注入 | Claude Code 的编辑器扩展：共享打开的文件与选区 | 需要编辑器在场 | 把编辑器的观察结果喂给模型 |
| 常驻语义索引 | Cursor、Windsurf 这类 IDE 原生产品 | 索引及其维护是产品本体 | 精确的定义、引用与类型查询 |

阶梯上的一个关键区分：第四级的做法，是把编辑器的**观察结果**（当前打开的文件、选中内容）注入上下文，而不是把 LSP 的**查询能力**交给模型。共享观察只需要文本通道；共享查询能力则要维护有状态的会话进程——预热延迟、每语言一个 server、崩溃恢复都随之而来。这解释了 pi 的选择：为一个更准的“查找引用”常驻进程，在多数任务上是负资产。

无论停在阶梯的哪一级，信息都必须进入模型的观察路径，或者被确定性的控制逻辑使用——工具升级改变的是供给质量，不改变闭环本身。升级的判据也不是仓库规模这类先验条件，而是失败观察：模型在同一种检索失败上反复打转、任务以大规模精确重构为主、文本搜索噪音超过收益时，逐级向右尝试——先临时脚本，再 repo map，最后才是常驻索引。这也是第四部分方法论的预演：先建立可观察的闭环，再根据失败增加机制。

假设要修复缓存失效问题，只读缓存函数可能不够。约束还可能存在于事务提交路径、并发调用方、配置和测试中。

因此，可靠性问题包含两层：模型是否正确理解已读信息，以及它是否取得足够的信息。精确替换检查能防止改错文本，却不能证明修改符合业务语义。

## 第四部分：如何理解 pi 的极简思路？

Mario Zechner 在 2025 年的设计文章中强调上下文控制和可观察性，采用短提示词与 read、write、edit、bash 四个基本工具。他倾向于把计划写入文件、按需使用 CLI 和 tmux，并通过自己的审查参与验收。这是其当时的设计与个人工作方式，不是所有 Agent 的通用规范。[作者原文](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/)

本教程从中提炼出的设计方法是：先建立可观察的闭环，再根据失败增加机制。

例如，计划文件有明确存储位置，人可以检查和编辑，新会话也可以重新读取。但文件存在并不保证模型会遵循它；读取时机、更新规则和完成检查仍需要设计。

同样，少量通用工具给模型较大的组合空间，专用工具则可以规定更清晰的操作与反馈。选择哪一种，要看任务和模型的实际表现。

作者的产品偏好、机制的实验效果和团队的运行要求，应分别评估。当前官方也把 pi 定位为可定制的 Harness，通过扩展等方式适配工作流。[pi 官方仓库](https://github.com/earendil-works/pi)

## 第五部分：增加机制时要付出什么？

下面是设计时可以采用的分析框架，不是已经验证的性能结论。

| 机制 | 想减少的失败 | 需要承担的成本或边界 |
|---|---|---|
| 计划与任务记录 | 长任务遗漏步骤，恢复时丢失进度 | 更新记录的成本，记录与实际状态不一致 |
| 上下文压缩 | 请求超限，旧信息占用预算 | 摘要遗漏或误述，重要细节失去原始依据 |
| 子 Agent | 独立研究或审查，分担上下文与工作 | 信息交接、预算、取消、共享文件冲突 |
| 代码索引与语义查询 | 搜索遗漏定义、引用或类型关系 | 索引更新、语言支持与工具维护 |
| 专用编辑工具 | 文本操作歧义或误改 | 参数与行为设计，模型适配 |
| 权限与执行隔离 | 误操作造成越界影响 | 权限策略、环境配置和使用成本 |
| 独立完成检查 | 模型过早报告任务完成 | 验收覆盖不足，检查成本或误判 |

这些机制可能同时影响成功率、成本和操作风险。不能只用一个指标概括它们的价值。

例如，审查子 Agent 可以提供独立观察，但与主 Agent 使用相同假设时仍可能漏掉相同错误。权限边界应由执行环境实施；仅让模型答应“不要修改”不能形成强制边界。

## 第六部分：什么才算可靠？

要分别检查不同对象：

| 对象 | 需要回答的问题 |
|---|---|
| Harness 实现 | 消息是否完整，参数是否验证，中断与恢复是否符合约定？ |
| 任务完成 | 产物是否存在，要求的操作是否完成？ |
| 代码正确性 | 是否满足需求，边界条件与回归是否检查？ |
| 可维护性 | 是否符合项目结构，复杂度和依赖是否合理？ |
| 操作安全 | 行动是否在授权范围内，影响是否受控？ |

前七章的离线测试主要检查本地实现和协议行为。它们不证明真实模型能完成任意编程任务。模型不再请求工具，也只是停止条件，不能直接作为独立验收。

例如，需求是“连接断开后自动重试，但业务错误立即返回”。测试只覆盖断线重试，就不能发现业务错误也被重试的问题。验证首先要覆盖需求中的区别，而不只是重演实现路径。

## 第七部分：Benchmark 能证明到哪里？

作者公开了 pi 配合 Claude Opus 4.5 的 Terminal-Bench 2.0 实验，完整运行每题五次。公开结果的平均指标约为 47.9%，也记录了执行错误；适配器代码可供复现。这是特定配置的历史结果，不是当前所有 pi 配置的表现。[原始结果](https://gist.github.com/badlogic/f45e8f6e481e5ab7d3a50659da84edaa)、[评测适配器](https://github.com/badlogic/pi-terminal-bench)

它支持极简方案可以完成一批有难度的任务，无法单独证明每一种被省略的机制都没有价值。要判断某机制的效果，需要控制其他变量。

Benchmark 的通过条件也有边界。一项针对其他三个工具的 SWE-bench Verified 研究发现，通过评测的补丁仍可能有错误，研究中的问题合计使解决率高估约 6.4 个百分点。该研究没有评测 pi，不能把其错误率套用到 pi 上。[研究论文](https://software-lab.org/publications/icse2026_SWE-bench-correctness.pdf)

因此，分数可以提供比较证据，还需要检查验收覆盖、失败原因，以及任务与实际项目的相似程度。

## 第八部分：怎样验证自己的 Harness？

假设我们想知道“加入计划文件流程是否有帮助”，可以做一个小规模的受控实验：

1. 选取一组真实历史任务，保留任务开始时的仓库状态，避免给模型泄露参考补丁。
2. 提前定义验收条件，使用独立测试和必要的人工检查。
3. 固定模型版本、推理设置、工具、运行环境和预算。
4. 比较原有流程与加入计划流程的版本，其余条件尽量相同。
5. 对每个任务重复运行，保留完整轨迹，按任务配对比较。
6. 同时记录成功率、成本、用时、人工修正量和失败类型。

多次尝试只要一次成功的指标，不能当成单次成功率；请求错误、超时和重试也应有一致的统计规则。如果加入子 Agent，应统计全部调用成本。

任务少时，结果可以用来发现问题和提出假设，不能轻易推广。增加机制后若成本明显上升，也需要判断成功率提升是否值得。无论结果是否符合预期，都应检查它实际减少了哪类失败。

## 回到 mini-pi

前七章已经提供了可以开展这种实验的基础：Provider、工具、会话轨迹、压缩、扩展钩子和 Skill。第 5 章的扩展可以承载策略，第 4 章的 JSONL 可以保存观察依据。

但评估必须区分两件事：确定性测试检查机制是否按约定实现，任务实验检查机制是否改善模型行为。一个“计划钩子被调用”的单元测试，不足以证明计划提高交付质量。

## 练习

### 练习 1：分析一次失败

选择一条失败会话，找出最早可以观察到偏差的位置。判断原因属于信息缺失、理解错误、工具失败、状态丢失，还是验收不足。引用原始消息和实际文件状态，提出一个能被后续实验检验的改进假设。

### 练习 2：比较一种机制

从计划文件、额外检索或独立审查中选一种，设计配对实验。先写下任务、预算、验收和成本统计方法，再运行。报告每项任务的结果与失败原因，并说明证据能支持到什么范围。
